## 一、产品现状梳理

### 1.1 定位与价值主张

**一句话定位**：面向美业门店乐龄女性客户的"健康测评 → 风险筛查 → 体检转介 → 门店养护方案"闭环平台，以"规则引擎定骨架、AI 只写文案、红旗不交给 AI"为安全底线。

**价值主张拆解**（已在代码中验证成立）：

| 角色 | 得到的价值 | 代码证据 |
|---|---|---|
| 客户（乐龄女性） | 免费六维测评与体检券、个性化养护方案、健康档案、魔镜 AI 陪伴、家人协同 | 测评 → `assessment.service` 红旗判定 → 体检券 → 预约 → 医院回传 → 方案自动调整，全链路可跑通 |
| 门店（顾问/店长） | 客户健康分层、待办工作台、方案三版文案、移动建档与禁忌确认 | 移动工作台 `/#/m`、健康档案表数字化（`admin.controller` intake 表单）、服务前禁忌确认 |
| 医院 | 转介单、号源日历、医生回传、对账 | `hospital.controller`（接收/拒绝/预约/到院/回传，未授权 C4 时回传置灰） |
| 平台 | 从测评到门店项目的转化漏斗、北极星指标看板 | 42 处 `wf.event` 埋点、admin 数据模块 9 类报表 |

### 1.2 目标用户与核心场景

- **主力用户**：50–70 岁乐龄女性（≥60 自动乐龄模式，`app.controller.ts:156` issue #8 已实现）、30–55 岁标准模式女性（李女士 persona）、高净值臻享客户（陈总 persona）。
- **核心场景闭环**（演示脚本与代码一致）：扫码/登录 → 60 题六维测评（分支题、L3 红旗立即跳紧急页 `question.vue:63-67`）→ 结果页三件事 + 体检券 → 预约（C3/C4 独立开关默认不勾）→ 医院回传"暂停重手法" → 方案自动再生成 → 顾问 48h 内跟进发送。
- **三条辅助场景线**：魔镜陪伴（双通道风险分类 + 固定安全话术 + 预警）、游戏化留存（打卡/问答/翻牌/消消乐/种树/转盘 + 健康存折）、家人协同（邀请 72h 有效、逐项可见范围 C6）。

### 1.3 产品亮点（评审中确认的差异化优势）

1. **合规设计领先同类 MVP**：C1–C9 九类授权独立管理、撤回有后果提示、健康数据查看写审计日志、医疗推荐不分等级、数据来源三色标签、鹰眼设备合规拦截（`pending` 状态不入引擎）。
2. **规则引擎架构正确**：`engine/` 纯函数无 I/O，服务端计算与后台模拟共用同一份代码；JSON Logic 规则存库可后台编辑并跑 7 例回归集。
3. **乐龄适老化不是贴皮**：一页一题、自动朗读、语音作答、30 秒坐站/单腿站立实体小测、演示助手代填，深入到交互层。
4. **AI 兜底策略成熟**：未配置大模型时全部功能走模板可用；魔镜高风险不调模型、直接固定话术 + 安全卡片 + 120/12356 热线。

## 二、多维度评估与问题清单

### 2.1 用户价值 ★★★★☆
业务闭环完整、三条留存线齐备。**短板**：
- 积分兑换商品（`app.controller.ts:33` REDEEM_ITEMS）与权益对照表（`:18` BENEFIT_TABLE）**硬编码在控制器里**，运营无法在管理端调整，与"配置驱动"的整体架构不一致。
- 门店预约是"24 小时内顾问电话确认"的意向单，无床位数/排班/时段选择（Q19 未解决），对高频到店客户摩擦大。

### 2.2 功能完整性 ★★★★☆
v1.0 页面清单 41 页基本全数落地，照片对比/记忆提取按计划推迟 V1.2。**短板**：
- 微信登录是模拟的（`app.controller.ts:49` openid = code 的 sha256，无 code2Session）；订阅消息、企微、支付均为占位。
- 小程序端语音识别依赖浏览器能力，微信端"同声传译"插件未接入，乐龄语音作答在真机小程序上不可用。

### 2.3 交互体验 ★★★★☆
细节质量高：换题回顶（`question.vue:53`）、完成关卡防连点（`:131`）、token 失效防重复跳登录（`request.ts:41`）、换账号清理本机缓存（`store.ts:21`）、图片加载失败占位。**短板**：
- 答题进度"第 X 题，共 Y 题"是**关卡内进度**而非全局 60 题进度，乐龄用户容易误判"还要做多久"。
- 语音匹配是简单字符串包含（`question.vue:156`），稍长回答即失配，仅提示重说，无二次降级引导。
- 魔镜非流式输出（一次返回 + 前端逐字），15 秒超时内无进度反馈，弱网下体感"卡死"。

### 2.4 易用性（乐龄视角） ★★★★☆
乐龄模式覆盖字号/间距/朗读/语音，登录流程固定标准样式避免新用户被放大（issue #3）。**短板**：
- 60 题 + 2 个实体小测的绝对时长仍偏长，中途退出虽逐题保存（好），但无"还剩约 N 分钟"预期管理。
- 错误提示统一 toast 2.5 秒（`request.ts:50`），对老年用户偏快且部分文案（"网络不太好"）未区分场景。

### 2.5 性能与稳定性 ★★★☆☆
**问题（均为代码实证）**：
- `/app/me` 一次请求 **8 个串行 await**（customer → store → advisor → unread → family ×2 → coupons → balance，`app.controller.ts:126-139`），魔镜 `context()`、`JobsService.tick()`（每条预警再查一次 customer）同为 N+1 串行模式。
- 定时任务是**进程内 setInterval**（`jobs.service.ts:22`）：重启窗口内 L3 升级/券过期静默丢失；单实例假设无法水平扩展。
- 无缓存层：首页配置、题库、规则等热点数据每次落库查询。
- API + 管理端静态资源 + H5 静态资源**同进程**（`main.ts:27-34`），一端流量尖峰互相影响。
- 小程序包体未做主包体积审计（static 200KB 起步 + UnoCSS safelist，暂无风险但需纳入 CI 监控）。

### 2.6 扩展性 ★★★☆☆
- 优点：monorepo 三端清晰、规则/题库/首页布局全部可后台配置、SQLite→MySQL 仅改 provider、演示沙箱按设备隔离。
- **短板**：
  - **服务端零单元测试**（全仓仅 miniapp 有 6 个 unibest 脚手架自带测试，非业务代码）。规则引擎承担 L2/L3 人身安全判定，v1.0 要求 100% 规则覆盖，当前仅 7 个后台回归用例。
  - 无输入校验框架（未引入 class-validator/ValidationPipe，全部手工解构 body）；无 helmet、无限流（`@nestjs/throttler` 未安装），`cors: true` 全开放。
  - JWT 密钥回退到 `'xueji-hackathon-demo'`（`auth.ts:7`），且**接受 URL query 传 token**（`auth.ts:23`，会进访问日志）。

### 2.7 安全与合规（MVP 特有的高危项）
- **手机号即登录**（`app.controller.ts:89` `/app/auth/phone`）：输入任意手机号即可登录/创建账号并查看该号对应客户的健康档案。内网演示可接受，一旦对公网开放或导入真实客户数据即为**重大隐私事故**。
- 敏感健康数据明文存储（`_enc` 加密未做，文档已列高优先回补）。
- 管理端演示密码统一 123456、无图形码/动态码。

## 三、分级优化建议

### 🔴 高优先级（影响安全底线或核心可信度，建议 1–2 周内完成）

| # | 问题依据 | 优化方案 | 预期收益 |
|---|---|---|---|
| H1 | 服务端零测试，规则引擎承担人身安全判定（13 条红旗、24 条禁忌） | 为 `engine/` 每条红旗/禁忌规则补"命中/不命中"两例单测（预计 ~80 例），接入 CI 作为合并门禁；后台 7 例回归集保留为集成冒烟 | 规则改动可回归；演示转生产的安全声明有据可依；这是文档自认的 P0 |
| H2 | 手机号即登录 + query 传 token + JWT 默认密钥 | ① 真实 `code2Session` + 手机号快速验证组件（需 Q20 AppID/Secret）；② 过渡期至少给 `/app/auth/phone` 加设备号+频控绑定；③ 删除 query token 分支，密钥缺失时启动即报错退出 | 消除"任何人可看任意客户健康档案"的最严重风险；token 不再泄漏进日志 |
| H3 | 无输入校验、无限流、CORS 全开（`main.ts:13`） | 引入 `class-validator` + 全局 `ValidationPipe`；`@nestjs/throttler` 对 auth/mirror/lead 类接口限流；CORS 收敛为显式域名白名单；加 helmet | 防爆破、防脏数据入库；公网部署前置条件 |
| H4 | `/app/me` 8 串行查询、Jobs N+1、魔镜 context 串行 | `Promise.all` 并行化三个热点（半天工作量，Prisma 无需改动）；`tick()` 改 `findMany({ include: { customer } })` | 首页/我的页 P50 延迟预计降 40–60%；VPS 低配环境收益更明显 |
| H5 | 积分兑换、权益表硬编码在 `app.controller.ts` | 迁入 `sync-config.ts` 配置域，管理端"营销-存折规则"页扩展维护 | 运营自助调权益与兑换品，兑现"配置驱动"承诺，不动代码上线 |

### 🟡 中优先级（影响规模化与真实运营，建议 1–2 月内排期）

| # | 问题依据 | 优化方案 | 预期收益 |
|---|---|---|---|
| M1 | SQLite 单文件 + 进程内定时任务，重启丢任务、不可横向扩 | 按文档计划迁 MySQL；任务迁 Redis + BullMQ（L3 升级这类 SLA 敏感任务优先） | 支撑真实门店并发；SLA 任务不丢 |
| M2 | 60 题时长长、进度感知弱、语音匹配脆弱 | ① 全局进度条（X/60，含预估剩余分钟）；② 语音失配 2 次后自动降级提示"直接点选也行"；③ 评估埋点漏斗定位流失题 | 降低测评中断率——测评是全漏斗入口，完成率每 +1pct 直接放大后续所有转化 |
| M3 | 魔镜非流式、15s 无反馈 | HTTP chunked + `enableChunked` 逐字输出（文档已列低优先，但弱网演示体验损伤明显，建议提前） | 陪伴感显著提升；演示时减少"卡住"尴尬 |
| M4 | 小程序端语音作答不可用 | 接入微信"同声传译"插件替换浏览器识别（H5 保留现状） | 乐龄核心卖点在真机小程序可用，而非仅 H5 |
| M5 | 站内消息触达弱 | 订阅消息（体检前提醒、方案发送、预警通知家人）；预警升级链路对接企微自建应用 | L3 预警 30 分钟 SLA 依赖主动触达，站内信无法保证 |
| M6 | 敏感字段明文 | `_enc` AES-256-GCM 字段加密先行落地（健康档案表、医院报告、魔镜记忆三张表优先） | 真实客户数据入场的前置条件 |

### 🟢 低优先级（体验与增长增强，V1.2 后排期）

| # | 问题依据 | 优化方案 | 预期收益 |
|---|---|---|---|
| L1 | 错误提示单一 | toast 按错误类别分级（网络/权限/业务），乐龄模式延长至 4s 并配震动 | 减少老年用户"看不见提示"的卡点 |
| L2 | 首页/方案页尚未完成美团风格第二步（文档 P1 待做） | 按文档计划推进，补门店实拍图授权 | 与美团进店心智一致，降低客户认知成本 |
| L3 | 预约无时段选择 | 门店端维护床位数/排班（依赖 Q19），意向表单升级为可选时段 | 到店转化体验升级 |
| L4 | 三端静态资源同进程 | API 与静态资源分离（Nginx 托管静态 / 或独立容器） | 流量隔离，故障域缩小 |
| L5 | 无 A/B 能力 | 首页配置已版本化，天然支持 A/B，补分流与指标归因 | 首页 6 套布局可用数据说话 |

## 四、潜在风险与遗留问题

### 4.1 风险清单

| 风险 | 等级 | 说明 |
|---|---|---|
| 真实数据提前入场 | 🔴 | 若演示后门店急于录真实客户，而 H2/M6 未完成，健康数据将明文+弱鉴权暴露。**建议管理端加"演示模式"横幅与真实数据开关** |
| 医疗合规边界 | 🔴 | 鹰眼设备 P19 处于合规拦截是对的，但 Q25（法务审核团购标题"558 项健康评估"）未闭环；AI 生成方案文案未接内容安全接口（msgSecCheck），一旦接公网大模型属必做项 |
| 单点故障 | 🟡 | 单 VPS 单进程单 SQLite 文件，无备份策略文档化；`data/xueji.db` 损坏即全量丢失。**建议立即加每日 cron 备份 + 异机留存**（成本极低） |
| 规则误判无兜底 | 🟡 | 禁忌标签（Q24 热疗/仪器/手法属性）由商学院人工确认中，确认前 warn 级项目照排进方案，存在操作风险；建议确认完成前 warn 项默认降级为"顾问当面确认后执行" |
| 微信平台依赖 | 🟡 | AppID、备案域名、request 合法域名均未办理（Q20/Q21），真机小程序验证被阻塞，越晚办理越晚暴露兼容问题 |

### 4.2 遗留技术债（文档已如实自报，此处确认属实）
MySQL/加密/真实登录/短信码（高）、Redis 队列/COS/企微/订阅消息/ASR-TTS（中）、流式输出（低）——与代码现状一致，无隐瞒。

### 4.3 迭代路线图建议（面向"黑客松 MVP → 单店试运行"）

```
里程碑 0（本周，演练加固）      里程碑 1（第 2–3 周，安全底座）     里程碑 2（第 4–8 周，真机上线）
├─ H4 查询并行化（半天）        ├─ H2 真实微信登录 + 手机号验证     ├─ Q21 域名备案 + HTTPS + 域名白名单
├─ SQLite 每日备份 cron         ├─ H3 校验/限流/helmet/CORS         ├─ M2 测评漏斗优化（先埋点后改版）
├─ H5 兑换配置外置              ├─ H1 引擎单测 + CI 门禁            ├─ M4 同声传译插件（真机语音）
├─ 演示模式横幅/数据开关        ├─ M6 敏感三表字段加密              ├─ M5 订阅消息（体检/方案/预警）
└─ 管理端弱密码强制改密          ├─ M1 前置：备份验证 + MySQL 演练    └─ 小程序提审（类目/隐私接口声明）
                                                                     ↓
                              里程碑 3（第 9–12 周，单店试运行）
                              ├─ Q19 床位/排班 → 时段预约
                              ├─ Q24 禁忌标签确认 → warn 项收紧
                              ├─ 企微自建应用（免登+预警推送）
                              └─ 真实客户灰度导入（50 人）+ 北极星基线
```

**节奏原则**：安全项（H1–H3、M6）先于任何真实数据导入；测评完成率是北极星漏斗的第一道闸门，M2 的埋点应在里程碑 1 就随版发出，先拿数据再改版；微信资质办理（Q20/Q21）行政周期长，**本周即启动**，与开发并行。
